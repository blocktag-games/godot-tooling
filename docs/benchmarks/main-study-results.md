# BP10 main study results: GDScript coverage-collection overhead

Generated by `pilot/performance/main_study_report.py` from `main_study_results.tsv` and `main_study_sessions.jsonl`. Protocol: [performance-protocol.md](performance-protocol.md). This report estimates effects; it does not declare a winner.

## What was run

- 1200 fresh-process runs: 10 sessions x 6 matched blocks x 20 eligible (candidate, workload, condition) cells, 3.65 hours wall time, one sitting (2026-09-20).
- Candidates: gd-tools-cli 0.4.0 via GUT (B0/B1/C) and Nano Coverage via GdUnit4 (B0/C; it has no real B1 and none was synthesized).
- B0 = collector absent; B1 = collector installed but inactive; C = collection active. Each candidate is compared only against its own baseline under its own runner.
- Engine: Godot 4.7.1.stable.official.a13da4feb (sha256 `32f8d7596c4b4118...`). Host: 11th Gen Intel(R) Core(TM) i7-11850H @ 2.50GHz, 16 logical cores, kernel 6.12.107+deb13-amd64, LMDE 7 (gigi), AC power.
- No profiler or debugger attached in any run.

Baselines moved by at most about 3% across 3.6 hours. The one visible time-order pattern is gd-tools W03, whose C/B0 ratio declines by roughly 1.5% from the first three sessions to the last (12.52 to 12.33) while its baseline rises about 1%. That is small against a 12x effect but it is a mild violation of the independent-sessions assumption, so that cell's interval is probably slightly too narrow. This machine has no thermal telemetry, so drift is inferred from the timings, not measured.

## Reading the results

- Coverage cost depends strongly on what the code does. Tight branch-heavy loops (W03) slow down by roughly an order of magnitude under both tools; a mixed scene workload (W11) by roughly 4x; signal dispatch (W05) barely at all under gd-tools and about 3x under Nano Coverage.
- gd-tools' installed-but-inactive mode (B1) costs essentially nothing: every B1/B0 estimate is within 0.4% of 1.0. Only one interval excludes 1.0 (W11 process interval, +0.4%, about 22ms), which is too small to matter.
- For an empty application (W01) either tool adds well under half a second to the whole run.
- Compare the tools by absolute added seconds on the same fixed work, not by percentage. Both run the identical workload source at near-identical baseline work times, so work-time deltas are the fairest cross-tool figure here.

## Limitations

- One Linux workstation, one engine build, one sitting. This is a deliberate scope decision (BP12 descoped), not a sample of machines.
- Ten sessions give df=9. Intervals are per-cell, not simultaneous across the table, and no multiplicity adjustment was applied.
- Sessions ran consecutively the same day (protocol amendment of 2026-09-20), which is more exposed to undetected drift than a multi-day spread.
- gd-tools runs headless; GdUnit4's runner opens a window. Process-interval floors therefore differ by runner and are not comparable across tools.
- Instrumented source scope is not identical: Nano Coverage also instruments the test-suite files (13 files vs 9).
- Four synthetic workloads. No real-project case study (W12) has been run.
- CPU time and memory were not measured; only wall-clock spans.
- gd-tools reports branch counters and Nano Coverage reports none, so the two tools are not doing identical collection work under C.
